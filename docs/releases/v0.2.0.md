# jobpayload v0.2.0

## Highlights

- **New: `jobpayload snapshot --check`.** It detects *snapshot drift*: whether
  the current code still serializes each snapshot case exactly as its stored
  baseline fixture. Run it in CI to fail when a change alters the payloads new
  code enqueues. It is read-only, its output is deterministic, and its exit
  codes follow the same 0 / 1 / 2 convention as `check`.
- **Race-safe baseline reads.** `snapshot --check` opens each baseline without
  following symlinks or blocking. It then checks that the open file is the one
  it inspected before reading it.
- **No breaking changes.** `snapshot`, `snapshot --update` and `check` behave
  exactly as in 0.1.0. The fixture schema (`jobpayload_schema: 1`), the JSON
  output schema (`schema_version: 1`), finding codes and exit codes are
  unchanged.

## Snapshot Drift Detection

```sh
bundle exec jobpayload snapshot --check
bundle exec jobpayload snapshot --check --format json
```

`snapshot --check` boots your application and serializes every case in your
cases file, exactly as `snapshot` would. It then compares the result with the
fixture already stored in `--output` (default `test/jobpayload_fixtures`).

- **Read-only for fixtures.** Nothing in `--output` is written, created,
  renamed or deleted, not even a missing `--output` directory. It cannot be
  combined with `--update`. Like `snapshot`, it still boots your application
  and runs your cases file.
- **Strict comparison of the `job` object.** The current payload is normalized
  the way `snapshot` writes it. The stored baseline is compared as stored and
  is never re-normalized, so an edited baseline is reported, including edits
  to volatile metadata such as `job_id` or `enqueued_at`.
  - Ignored: `source` metadata (Ruby, Active Job and jobpayload versions), key
    order, whitespace and equivalent JSON spellings.
  - Kept: value types (`1` vs `1.0`, `null` vs a missing key) and array order.
- **Deterministic output.** Text output has one line per case and a summary.
  JSON output uses `schema_version: 1` and `"mode": "check"`.

| Status | Meaning | Exit |
| --- | --- | --- |
| `identical` | The stored baseline matches what the current code serializes | 0 |
| `different` | The current code writes a different payload | 1 |
| `missing` | No baseline fixture for the case | 1 |
| `invalid` | The baseline cannot be used (see below) | 2 |

A baseline is `invalid` when any of these hold:

- it is not valid schema v1 JSON
- it is a symbolic link (never followed, even to a valid fixture)
- it is not a regular file
- it cannot be read
- it was replaced or removed during the check
- it holds a `job` that `snapshot` could never have written

When results are mixed, the highest exit status wins (`2` > `1` > `0`).
Configuration, boot and case errors also exit 2. Fixtures with no matching case
are ignored.

**How it differs from `check`.**

- `check` answers "can the *new* code still deserialize payloads written by
  the *old* code?" (backward-read compatibility).
- `snapshot --check` answers "does the current code still *write* the payloads
  recorded in the baseline?" (drift).

They are complementary. A `different` result is not a compatibility failure by
itself: keep the old fixture for `check` and add a case for the new format, or
re-run `snapshot --update` if the baseline should follow the code.

## Security Hardening

`snapshot --check` reads each baseline in four steps:

1. `lstat` the fixture path. Anything that is not a regular file, a symbolic
   link included, is `invalid` and is never opened.
2. Open the fixture read-only with `O_NOFOLLOW` and `O_NONBLOCK`. A symbolic
   link put in its place is refused, not followed, and a FIFO put in its place
   cannot block the open. The open never creates or truncates anything.
3. `fstat` the open descriptor. It must be a regular file with the same
   device and inode numbers `lstat` reported.
4. Read only from that verified descriptor. The path is never opened again.

An entry that is replaced after step 1 is reported as `invalid` (exit 2) and
never read. That covers a symlink (including one to a file outside the
fixtures directory), a FIFO, a directory, another regular file (even one with
identical content), and an entry that was removed. Such a swap cannot leak
file contents into the output, block the check, or make it pass. If the
platform lacks `O_NOFOLLOW` or `O_NONBLOCK`, every baseline is `invalid`
rather than read without them (fail closed).

**Impact.** `snapshot --check` is new in this release, and this hardening was
added before it was released. No released version of jobpayload is affected.
`jobpayload check` is unchanged: it reads fixtures by path and follows
symbolic links, as in 0.1.0.

## Reliability and Compatibility

- **Supported matrix tested in CI:** Ruby 3.3, 3.4 and 4.0 × Active Job 7.2,
  8.0 and 8.1, nine combinations on Linux.
- **macOS smoke job** (Ruby 3.4, Active Job 8.1). Tests that need file names
  which are not valid UTF-8 are skipped there based on a file-system
  capability probe, because APFS rejects such names.
- **Rails `main` regression workflow** for GlobalID handling. It runs on pull
  requests, weekly and on demand. Rails `main` is *not* a supported version;
  this workflow only gives early warning of upstream changes.
- **New tests** cover `snapshot --check`:
  - read-only behaviour
  - deterministic output
  - exit precedence
  - deep JSON
  - baselines replaced between `lstat` and `open`, in-process and in real
    processes
  - FIFO deadlines
  - descriptor leaks
  - `check`'s unchanged symlink handling

## Installation / Upgrade

```ruby
# Gemfile
group :test do
  gem "jobpayload", "~> 0.2.0", require: false
end
```

```sh
bundle update jobpayload
bundle exec jobpayload --version   # jobpayload v0.2.0
```

Existing fixtures keep working and do not need to be regenerated. Fixtures
written by 0.1.0 record `"jobpayload_version": "0.1.0"` in their `source`
metadata. `snapshot --check` ignores `source`, so the version bump alone
never makes a baseline `different`. `snapshot` without `--update` never
rewrites an existing fixture. The first `snapshot --update` after upgrading
rewrites every fixture once, because each one's `source.jobpayload_version`
changes to `0.2.0`; the `job` payloads themselves stay the same.

## Known Limitations

- **Race-safe reads cover the final path component only.** Parent directories,
  including a `--output` directory that is itself a symlink (allowed), are
  trusted. These are not detected:
  - replacing a parent directory
  - another process rewriting the verified file's contents in place
  - hard links
  - inode reuse
  - behaviour specific to network or unusual file systems

  Something swapped in after `lstat` is opened before `fstat` rejects it, so
  opening some device nodes can still have side effects.
- **`check` still follows symbolic links** and reads fixtures by path, as in
  0.1.0.
- **jobpayload never performs, enqueues or retries jobs.** A successful
  deserialize does not prove the job behaves correctly.
- **Queue backend storage formats are not checked.** jobpayload works on
  Active Job's serialized job data, not Sidekiq, GoodJob, Solid Queue or other
  backend formats.
- **`snapshot --check` does not show field-level (structural) diffs.** It
  reports whether a baseline differs, not where. Compare the files, for
  example with `git diff` after `snapshot --update`.
- Duplicate keys in a fixture are handled by your json gem version (last value
  wins before json 3; json 3 rejects them), for both `check` and
  `snapshot --check`.
